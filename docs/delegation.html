Using it

Delegating work

An agent can create a whole new session — on either backend, on any model that backend offers — hand it a job, and carry on. This is the most useful thing in PodPrompt and the easiest to use badly.

What delegation is

delegate_session always creates something new. It takes a backend, a prompt, and optionally a title, a model, and whether to wait. What comes back is a @handle for a real session you can open, prompt, and read like any other.

That is the key difference from a sub-agent. A delegated session is not a task inside somebody's turn — it is a peer. It appears in the session list nested under its parent, it survives its parent, and you can talk to it yourself.

Delegate, or message?

delegate_session makes a new session. message_session talks to one that already exists. An agent that wants an answer from a colleague should message; an agent that wants a job done in parallel should delegate.

Async and awaited

By default delegation does not wait. The call returns the moment the child exists, the parent's turn can end, and when the child finishes, its final reply is delivered to the parent as ordinary mail — reported as delegated work finishing, with a pointer to read the transcript for detail.

Asking it to wait holds the parent's turn open until the child's turn ends, and returns the outcome and the child's final text directly.

Gotcha · An awaited result is not durable

Async results travel through the stored mail system, so they survive a restart. An awaited result is held in memory — if the driver restarts while the child is running, the result is lost even though the child keeps working. That is why async is the default, and why long jobs should not be awaited. If it happens, the child's transcript is still there; read it.

Async also means the user is not left staring at a spinner. A parent that delegates three jobs and ends its turn lets you keep working while they run.

What the child sees

A delegated session starts a completely fresh conversation. This is the single most important thing to understand, because a prompt written as though the child shares the parent's context will fail in ways that look like the model being stupid.

Does it inherit…
The parent's conversationNo
Anything the parent readNo
The parent's instructions or system promptNo
The working directoryYes
The same workspace filesYes
Auto-approveYes, and it tracks the parent's setting live
The modelOnly if no model was specified and the backends match

Because the workspace is shared, the right move is to refer to files by path rather than pasting their contents into the prompt. The prompt needs to carry the intent and the background; the files can speak for themselves.

Auto-approve reaches through to children

It is resolved through the parent relationship rather than copied, so changing it on a parent affects children that already exist. Useful, and worth remembering before you switch it on.

Backend and model

The backend is required — claude-code or opencode. This is how you get work onto the other backend without starting a session by hand, and it is one of the better reasons to delegate at all.

The model is optional and is checked against the target backend's own list, so a valid id for the other backend is still rejected. Omit it and the child takes the parent's model when the backends match, or that backend's default when they do not.

A wrong model id is cheap and self-correcting

An unrecognised id is rejected with the full list of ids that backend accepts, and nothing else happens — no session is created and it does not count against the per-turn limit. An agent that does not know the right id can simply guess, read the list from the rejection, and immediately try again.

Tracing it back

Delegation chains stay legible in both directions:

  • In the parent, a delegation bubble lists the children it created, with live status. OpenCode differs — no live status there; read the nested session row instead.
  • In the child, the opening prompt is labelled Delegated rather than as something you typed, and the parent's handle is a link that jumps to the exact bubble that created it.
  • In the session list, the child is nested under its parent — remembering that families start collapsed.

The status wording in a parent's delegation bubble distinguishes states that would otherwise all look like "done":

runningWorking.
waiting for your answerBlocked on a question — go and answer it.
waiting for your approvalBlocked on a permission card.
waiting out a usage limitWill resume on its own, with an estimate.
stopped by youDeliberate, and not coloured as a failure.
failed — retries exhaustedNeeds you.
out of creditWill not retry.

Watching it work

A delegated session is an ordinary session, so you can open it at any point and read along, prompt it directly, stop it, rename it, or detach it from its parent.

An agent can follow its own child too, with read_session — which is often better than waiting, since it can check progress without blocking.

Gotcha · Delegation is bounded three separate ways

A single turn may perform at most 8 messages and delegations combined. Sessions may only spawn sessions 6 levels deep. And the global autonomy budget caps automatic turns across everything at 20 by default — when it runs out, delegation is refused before a child is created rather than creating one that cannot start. See Running unattended.

Auto-delivery is on by default for delegated sessions, so mail reaches them even while you are reading them. That is usually what you want from something you spawned to do a job, and it is a per-session switch beside the composer if it is not.
