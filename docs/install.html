Getting started

Install & launch

Five steps to a working browser window. You set it up once, then run podprompt from whichever project you want to work on — the directory you are standing in becomes the workspace.

Prerequisites

You need Docker (Engine or Desktop), a browser, and a full checkout of this repository — not a few files copied out of it, because both the build and the viewer deployment read from the viewer/ tree.

Put the checkout somewhere permanent

The podprompt command finds the checkout from its own location every time it runs — that is what lets it work from any directory. So the checkout is permanent infrastructure, not scratch space. Move it or delete it and the command stops working until you update your PATH.

The launcher is a shell script and uses a handful of standard tools:

ToolUsed for
bash 3.2+The launcher deliberately avoids newer bash features so macOS's built-in bash works.
curlChecking the viewer is up, and talking to a LiteLLM proxy.
jqListing LiteLLM models, and tidying stale settings entries.
lsofClearing a stale process off the viewer port. Without it that cleanup silently does nothing.

No host Node.js or Python is needed. Both live in the image. No CPU architecture is pinned, so Linux x86-64, Intel Macs and Apple Silicon all build natively.

1 Put it on your PATH

The command lives at bin/podprompt in the checkout. Add that directory to your PATH and you can invoke podprompt from anywhere.

permanent — add to ~/.bashrc or ~/.zshrc 
export PATH="/path/to/podprompt/bin:$PATH"

Or, to try it in the current shell without editing anything, source the activation script. It works out where it lives, so there is nothing to edit:

this shell only 
source /path/to/podprompt/activate.sh

It prints the exact line to add to your shell profile when you want to keep it. Symlinking bin/podprompt into a directory already on your PATH works too — the command follows symlinks back to the real checkout.

Shells other than bash and zsh

The activation script needs bash or zsh. On fish, use fish_add_path /path/to/podprompt/bin instead.

2 Build the image

builds from the checkout, runnable from anywhere 
podprompt --build

This installs both agent backends — Claude Code and OpenCode — plus git, curl, ripgrep and Python 3, and bakes the viewer's Node dependencies into the image for its own platform.

When to rebuild

Whenever the Dockerfile changes, and also whenever viewer/package.json or viewer/package-lock.json changes — they are build inputs, so a dependency change needs a rebuild, not just a redeploy.

3 Deploy the viewer

copies the app to ~/.local/share/podprompt/viewer/ 
podprompt --deploy-viewer

The browser interface is the default way to use PodPrompt, so unless you only ever intend to use a terminal, this step is required rather than optional. It is a plain file copy — it installs no dependencies, since those are already in the image — and it will refuse to report success if the copy looks wrong.

Run it again whenever the app code in viewer/ changes.

4 Sign in

There are four ways to authenticate. The first three configure Claude Code; OpenCode always manages its own credentials separately.

A Claude subscription default

Nothing to configure, but there is an ordering requirement: the browser interface has no terminal for the one-time login prompt, so you must log in through a terminal session first.

once, to complete the browser sign-in 
podprompt --claude

After that the credentials live in ~/.claude on your machine and every later launch reuses them.

Gotcha · Do this before your first viewer launch

Skip it and the viewer starts, but Claude Code sessions inside it have no credentials and nothing explains why. This is the single most common first-run problem.

An Anthropic API key

Billed per token, and needs no interactive login. Put your key in an environment file — podprompt.env.template shows the format, and real credentials belong outside the repository, conventionally at ~/.podprompt.env.

Load the file before you launch

PodPrompt reads credentials from your environment; it does not read the file for you. Source it in the shell you launch from, or add the line to your shell profile so every new shell has it: 

source ~/.podprompt.env
  • ANTHROPIC_API_KEYrequired Your API key. Launch with --direct-api.
Gotcha · The template's placeholder counts as set

podprompt.env.template contains a literal sk-ant-… placeholder. Copying it without editing leaves the variable non-empty, so the launcher will not warn you — the request simply fails later. Replace the placeholder, don't just copy the file.

A LiteLLM proxy

See Using a LiteLLM proxy below.

OpenCode

OpenCode keeps its own credentials, so the provider flags above — which configure Claude Code — do not apply to it. (The one exception is --litellm, whose proxy details are passed through for OpenCode to use as well; see Using a LiteLLM proxy.) Log in through a terminal session once:

OpenCode's own login 
podprompt --opencode

That is the only manual step. Once you are signed in, OpenCode sessions in the browser just work — PodPrompt starts and supervises OpenCode's background server for you inside the container, and restarts it if it stops.

Not a valid combination

--opencode --direct-api is rejected outright. The API-key provider configures Claude Code, and OpenCode has nothing to do with it.

5 Launch

from whichever project directory you want to work in 
cd ~/some/project
podprompt

The launcher waits for the viewer to come up and then opens http://localhost:7843 in your browser. If it cannot open a browser for you, visit that address yourself.

The directory you launch from is the workspace. It is mounted at /workspace inside the container and is where agents do their work. Your ~/.claude directory is always mounted too, so sessions and credentials persist across launches.

Because the current directory is effectively an argument, every launch prints what it resolved to: 

Workspace: /home/you/some/project → /workspace
Launching from your home directory asks first

If the working directory is your home directory — or anything containing it, such as / — you get a warning and a confirmation prompt, because that would hand agents write access to everything you own. Answering yes proceeds; it is your machine.

With no terminal to prompt on, it warns and continues rather than breaking a script. Set PODPROMPT_YES=1 to skip the prompt deliberately.

The container itself is disposable — it is removed and recreated on every launch. Everything worth keeping lives on your machine through bind mounts, listed in the Reference.

Nothing is exposed to your network

The page and the driver are published to 127.0.0.1 only. The OpenCode server is never published outside the container at all.

Terminal instead

If you would rather have a plain terminal agent with no browser, pick a backend explicitly:

--claudeA Claude Code terminal session. --claude-code is the same thing.
--opencodeAn OpenCode terminal session.

These are mutually exclusive with each other and with an explicit --viewer; asking for two interfaces is an error rather than a guess. Unrecognised arguments are passed straight through to the underlying agent, so things like podprompt --opencode --continue work as you would expect.

Pass-through arguments and the viewer

In the default browser mode there is no terminal agent to pass arguments to, so they are reported and ignored. The viewer is unaffected and fully usable — pick your session in the browser instead.

Using a LiteLLM proxy

Set two variables and launch with --litellm:

  • LITELLM_URLrequired Base URL of the proxy. The shipped default is the literal placeholder <MY-LITELLM-URL>, so it must be set.
  • LITELLM_API_KEYrequired Key for the proxy. Also required by --list-models.

The launcher checks the proxy is reachable, then runs an interactive model picker so you can choose a primary model and optionally a small, fast one. To see what is available without launching:

list model ids and exit 
podprompt --list-models
Launch modeModel pickerRoute used
default viewer Runs Anthropic-format /v1/messages, for Claude Code sessions
--claude Runs Anthropic-format /v1/messages
--opencode Skipped OpenAI-compatible route, via OpenCode's own config

Your picks apply to the whole launch rather than to one browser session, and they are not remembered — choose again next time, or pass the model explicitly.

Claude Code only, with one exception

The provider flags configure Claude Code. OpenCode reads its own configuration instead — but --opencode --litellm does work: the proxy details are passed through for OpenCode to use via the OpenAI-compatible route.

Your own model providers

OpenCode can talk to any OpenAI-compatible endpoint — a local llama.cpp or Ollama server, a LiteLLM proxy, an institutional inference service — by adding it to ~/.config/opencode/opencode.jsonc. Each provider needs a base URL, a key, and a list of the model ids it serves.

That list is the annoying part. A provider with no models block contributes nothing at all, so you write the ids out by hand — and then they drift. A model added upstream stays invisible until you notice; one withdrawn upstream sits in your picker until a turn fails on it.

PodPrompt ships an optional OpenCode plugin that removes the list: it asks each provider what it currently serves and registers the answer, re-checking periodically. It lives in extras/model-discovery/ in the repository, with a README, a worked example of both files you need, and a self-test.

Opt in by hand

Nothing installs it for you. OpenCode's plugin directory is shared with any non-Docker OpenCode on the same machine, and a plugin that polls your endpoints on a timer is not something PodPrompt should put there on your behalf. Two cp commands, both in the README.

Gotcha · It uses an API OpenCode does not document

The way a plugin adds models to the catalog was worked out by experiment and verified against OpenCode 2.2.7. An OpenCode upgrade could change it. Run extras/model-discovery/verify/run.sh after upgrading — it checks the whole path against stand-in servers in about a minute, and needs none of your real providers to be running.

Discovered models appear a few seconds after startup rather than instantly, and a provider that is unreachable costs you only that provider: it keeps whatever it found last time and leaves the rest of your picker alone.

Reaching host services

By default the container is on a bridge network, which means it cannot reach something on your machine that listens only on loopback — a local model server on 127.0.0.1:8080, for instance. For that, use host networking:

share the host network namespace 
podprompt --host-network

This stops publishing ports and instead binds the viewer and driver directly to 127.0.0.1, so sharing the host's network does not put the driver's control plane on every interface of your machine.

macOS caveat

Needs Docker Desktop 4.34 or newer with Settings → Resources → Network → Enable host networking. Even then, reaching the viewer from the host browser can be unreliable on macOS. On Linux it works normally.

A custom image

Some work needs tooling the standard image does not carry — a headless browser, a language toolchain, a particular CLI. Build your own image on top of PodPrompt's, and point at it when you need it.

Write a Dockerfile starting from the base

Dockerfile.mytools — this can live anywhere 
FROM podprompt

# Install as root, then switch back.
USER root
RUN apt-get update && apt-get install -y --no-install-recommends \
        graphviz \
    && rm -rf /var/lib/apt/lists/*
USER agent
Gotcha · The base leaves you as a non-root user

It ends with USER agent, so apt-get fails on permissions unless you switch to root first. Switch back at the end, or your agents will run as root.

Build it with your own tag

a plain docker build 
docker build -t podprompt-mytools -f Dockerfile.mytools .

podprompt --build will not do this — it always builds the checkout's own Dockerfile and tags it podprompt. Passing --build and --image together is an error.

Run it

from the project you want to work on 
podprompt --image podprompt-mytools

Only one container runs at a time, so this swaps which image it uses rather than running two side by side. Your sessions, credentials and settings live on your machine rather than in the image, so switching keeps all of them. Leave the flag off to go back.

Nothing to add for the label

PodPrompt only runs images labelled org.podprompt.base. Docker passes labels down through FROM, so an image built on the base already has it.

Gotcha · Rebuilding the base does not update yours

After a podprompt --build, rebuild your own image too, or it is still sitting on the previous base.

When it won't start

SymptomCause and fix
An image was refused for having no label It does not descend from the PodPrompt base. Rebuild it FROM podprompt; see A custom image.
Told the image predates the label Your podprompt image is older than your checkout. Rebuild it with podprompt --build.
podprompt: command not found The checkout's bin/ is not on your PATH in this shell. If you sourced activate.sh, that only applied to the shell you ran it in — add the line to your shell profile to keep it. See step 1.
Told the image does not exist Run podprompt --build.
No viewer/ in this checkout The checkout has been moved, renamed or partly deleted. The command resolves it from its own location, so point your PATH at wherever it is now.
Told to run --deploy-viewer The viewer app isn't on your machine yet, or its files are incomplete. Run step 3 again — from anywhere, it finds the checkout itself.
Claude Code sessions have no credentials The one-time sign-in hasn't happened. Run podprompt --claude once, complete the login, then relaunch.
Launch aborts over a busy port Something unrelated to PodPrompt is on the viewer port, and the launcher will not kill a process it does not recognise. Move with --viewer-port, and pick a value that isn't 7844 — that is the driver's port.
OpenCode sessions have no messaging tools The deployed viewer is missing opencode-plugin.ts. Redeploy with step 3 rather than copying files by hand.
Arguments seem to be ignored They are, in browser mode — see above. Use --claude or --opencode if you need to pass agent arguments.
A dependency change had no effect --deploy-viewer copies app code only. Dependencies are baked into the image, so rebuild it.
