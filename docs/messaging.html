Using it

Sessions talking

Any session can find the others, message one, and read its transcript. This page covers how they address each other, what they can actually do, and the several reasons a message might be sitting still.

How it works

A message from one session to another is mail. It is durable — written down, not held in memory. Delivering it starts a turn in the recipient, or joins one already running. The sender does not wait for a reply; it gets a receipt saying what happened to the message, and if the recipient has something to say it messages back later.

That asynchrony is the whole design. Two agents are not in a conversation with each other; they are leaving each other notes, each acting on its own schedule.

Mail arrives as a Peer bubble

In the recipient's transcript, incoming mail shows up as a collapsed bubble with the sender's handle linked to their session, so you can always trace who prompted what. See The interface.

Handles

A session's address is a @handle derived from its title: lowercased, punctuation turned to hyphens, trimmed to 32 characters. Refactor the auth layer becomes @refactor-the-auth-layer. Clashes get a numeric suffix.

Handles are made as needed rather than claimed — there is no step where you register one. A brand-new session has no title yet, so it gets a placeholder like @session-2, which is upgraded once it has a real title.

What happens when a title changes

ChangeEffect on the handle
You rename the sessionThe handle follows the new title.
The backend re-titles it itselfNothing. Handles do not follow automatic summaries.
You set a handle explicitlyIt is pinned and never moves again, whatever the title does.
The new name is already takenThe title changes, the handle stays put. No silent -2 suffix.
Old handles keep working

Every name a session has ever answered to keeps resolving for as long as that session exists, and can never be taken by a different session. So renaming something mid-task strands nothing, and a genuinely stale handle fails loudly with "unknown handle" rather than quietly delivering to the wrong agent. Deleting a session frees its names.

What agents can do

Four tools, identical on both backends. You will see them in Tool bubbles, and knowing their options is useful because you can ask an agent to use them better.

Find the others

list_sessions returns the peers it can reach, most recently active first, with each one's handle, backend, title, whether it is idle or mid-turn, how it relates to the caller, and whether it has stalled. Optional search, limit and all.

Gotcha · It hides things by default

It excludes the caller, archived sessions and unreachable ones, and stops at 20. It always says how many it held back — if an agent says it cannot find a session, that count is usually why. Ask it to search by name or pass all.

Send a message

message_session takes a handle and some text. It returns a receipt immediately — delivered, delivered into a turn the recipient is already running, queued, or a refusal with a reason — never the recipient's answer.

It also takes resume, for reviving a session that list_sessions reported as stalled. That prepends the right continuation wording for however the turn died, with your text appended after it. If the target is not actually stalled, the receipt says so and nothing is sent.

Spawn a new session

delegate_session creates a session and gives it work. It always creates — it never addresses something existing. Covered in Delegating work.

Read a transcript

read_session reads any reachable session's transcript, including the caller's own — pass me. It takes search, role to filter to assistant, user or tool entries, from to start at a given entry, and last for the final few. Entry numbers are positions in the full transcript, and the header tells you how many there are.

It always reads the complete history regardless of what the interface is displaying — the point of the tool is to recover what rendering may have hidden.

Gotcha · It reads the end, not the beginning

With no from or last, it returns the most recent 10 entries, capped at 25, each truncated at 1,500 characters. To read from the start, from=1 is required and is not something an agent will necessarily think of. If you want early context recovered, say so.

Tool names differ by backend

Claude Code exposes them prefixed, as mcp__podprompt__list_sessions and so on. OpenCode registers them under bare names. Same tools, same behaviour.

Why mail waits

A message is not always delivered the moment it is sent. There are three reasons it might sit, and they are independent — clearing one does not clear another.

Being busy is not one of them. A session that is already working is the easiest to reach, not the hardest: the message joins the turn in progress. See Reaching a session that is busy.

The watching rule

Your browser tells the driver which session you are looking at. A session counts as watched for 120 seconds after the last time it reported you there. Glancing at another tab does not instantly dump held mail — that one grace period covers every way your attention can end, including closing the browser.

The hold applies only while the session is idle. The point of it is that a watched session you are about to type into should stay still until you are ready to move on — and you release it either by prompting it yourself or by accepting the mail. A session that is already working was never going to give you that turn anyway, so mail goes straight in. You can still take control at any moment with Stop.

Auto-deliver, next to the composer, switches this off for a session: mail arrives even while you watch. It is on by default for delegated sessions and off for everything else, on the reasoning that a session you spawned to do a job should get on with it.

Gotcha · Auto-deliver does not bypass the autonomy budget

It only overrides the watching hold. Mail still stops arriving when the global budget runs out — the budget is spent by whoever sends, so a chatty pair of sessions stops itself whether or not auto-deliver is on. And watching a session never refills that budget.

Approving mail

Held mail appears in the strip under the header, with a count and a list. Approval is per message. Approving two waiting messages does not approve a third that arrives a minute later — that one gets its own decision and shows up as a fresh arrival. Approvals also survive the turn that was running when you clicked.

The strip counts only mail genuinely waiting on you. Mail that is merely queued behind a busy session is not counted, so the badge does not flicker for things that resolve themselves.

Gotcha · A queued receipt does not say who is holding it

A sender is told whether its message was delivered, joined a turn already running, or was queued — but not why it was queued. An agent reporting that its message is "queued" may be waiting on your approval. Check the strip rather than taking the receipt at face value. Mail held by the autonomy pause is reported as not delivered, but it is stored and will flow when you resume — that one is not worth retrying.

Reaching a session that is busy

A session that is working does not have to stop to hear from anyone. Mail reaches it mid-turn: the message joins the work in progress rather than waiting for it to finish.

It arrives at the next natural break — after whatever tool the agent is running returns, not in the middle of it. Nothing is cancelled and no work is thrown away. The agent reads the message with its own task still in front of it and decides what to do: act on it now, or finish what it was doing first.

Why this matters for long jobs

It used to be that a session waiting on a reply had to end its turn to receive one. If the thing it was waiting for never came back, nobody was waiting and the work simply stopped — the sort of thing you discover the next morning. A session that never has to stop listening cannot get stuck that way.

The sender is told which happened. A receipt reads "delivered into the turn they are already running", "delivered now", or "queued" — so an agent can tell a message that landed from one that is still waiting, instead of guessing from silence and repeating itself.

Both backends work this way, so it is not something to plan a session around: whichever agent you pick, a long-running one stays reachable while it works.

How a batch arrives

When several messages are waiting for one session, they are delivered together — as a single turn if the recipient is idle, or as one entry into the turn it is already running.

For display they are taken apart again, so each sender gets its own Peer bubble with its own link. The same sender appearing twice in a batch stays two bubbles in the original order; nothing is merged. If the split does not look right, the whole batch is shown as one bubble rather than risk attributing text to the wrong sender.

This is worth exploiting

Because coalescing is per recipient, batching requests to one agent is cheaper than drip-feeding them. See the Playbook.

After you stop a session

If a session's last turn was ended by you pressing Stop, the next message delivered to it is prefixed with a note saying so — telling the agent to address the new message and reconsider, rather than assuming it should pick up where it was halted. Crashes and restarts do not get this; they get their own resume wording.

Your controls

ControlWhat it governs
Auto-deliverPer session, beside the composer. Whether mail arrives while you are watching that session.
Deliver / approveIn the strip. Releases specific held messages.
Messaging offPer session. Makes it unaddressable — other agents see it listed as not messageable.
HandlePer session. Pin a handle so it never follows a rename.
AutonomyGlobal. How many automatic turns may happen at all. See more.
Gotcha · Turning off messaging also turns off reading

Reading a transcript counts as interacting with it. A session with messaging disabled cannot be read by other agents either. Its handle still resolves — the refusal comes at the point of access, so the caller gets a clear denial rather than a confusing "no such session".
