Playbook

Patterns that get real leverage out of the machinery, and a triage list for the times it looks like nothing is happening. Each one explains why it works, so you can adapt it rather than follow it.

Fan out the reading

When answering a question means sweeping a lot of material — several subsystems, several possible naming conventions, a big dependency — ask an agent to delegate one session per strand rather than reading it all itself.

Why it works. Delegation is asynchronous by default, so all the strands run at once and each reports back as mail when it is done. The parent's context stays clean: it receives conclusions rather than filling up with file dumps.

Watch for: one turn may only start 8 messages and delegations combined. Beyond that, have the parent delegate in waves, or delegate a coordinator that fans out again — remembering the 6-level depth limit.

Ask for the shape of the answer

A delegated session's report is its final reply only. Tell it what the answer should look like and ask for it last, or you will get a sign-off sentence instead of findings. Having each one also write full detail to a file turns the mail into a summary and keeps the evidence.

Right model for the job

Delegation takes an explicit model. Use it: put mechanical work — inventorying, collating, reformatting, first-pass searching — on something cheap and fast, and keep your expensive model for the synthesis that actually needs judgement.

Why it works. The model is validated against the target backend's own list, and a wrong guess is rejected with the full list of valid ids while costing nothing — not a session, not a turn, not fan-out. An agent that does not know the id can guess, read the rejection, and retry immediately.

Watch for: model ids are backend-scoped. A valid OpenCode id is still rejected for a Claude Code child.

Batch, don't drip

If you have three things to tell one agent, send them together or in quick succession rather than waiting for each to be acted on.

Why it works. All mail waiting for one session is delivered as a single turn. Three messages that arrive together cost one automatic turn instead of three — and the shared autonomy budget is the scarce resource. They are still shown as separate bubbles per sender, so nothing is lost in readability.

Watch for: coalescing is per recipient. Sending to three different agents is three turns no matter how you time it.

Delegate or sub-agent?

Both run work elsewhere. They are not interchangeable, and picking wrong is a common source of frustration.

Use a sub-agent when…Delegate when…
  • The work is a self-contained lookup
  • You want the answer inside this turn
  • Nobody needs to talk to it afterwards
  • It is fine for it to vanish with its parent
  • The work is substantial or slow
  • You might want to prompt it yourself
  • It should outlive the turn that started it
  • You want it on a different backend or model

The deciding question is usually "will anyone need to talk to this later?" A sub-agent cannot be talked to at all, and promoting one afterwards gives you a session with an empty context — the transcript is readable, but the model has not read it.

Never await long work

An awaited delegation's result lives only in memory. If the driver restarts while the child runs, the result is lost — though the child keeps going and its transcript survives. Await quick things; let anything substantial come back as mail.

Ask the other backend

Both backends are always available, and a session is permanently bound to the one it was created with. Delegation is the way across.

For a decision you are unsure about — a design call, a diagnosis, a review — have one session delegate the same question to the other backend and compare. You get an independent read from a fresh context rather than a model agreeing with the conversation it is already in.

Watch for: the child shares the workspace but nothing of the conversation. Point it at files by path and state the question so it stands alone, or you will get an answer to a question it had to guess.

Recover your own context

An agent can read its own transcript. This is the fix for a long session that has compacted, or one that has lost the thread of something decided hours ago: ask it to search its own history rather than re-explaining.

Why it works. Transcript reading always uses the full history, regardless of what the interface is displaying — the tool exists precisely to recover what rendering may have hidden.

Watch for: it returns the most recent entries by default. If you want the beginning of a conversation, say so explicitly — reading from the first entry is not what it will reach for on its own. Searching for a distinctive phrase usually beats paging.

Also useful for watching a child

A parent can read a delegated session's transcript while it works, which is better than awaiting it: progress without blocking.

Name things early

A session's @handle comes from its title, and the title starts as whatever the backend guessed. Renaming a session you intend to keep gives it an address other agents can actually use — and your own instructions can name.

Why it is safe to rename later. Every name a session has answered to keeps resolving for as long as it exists, and can never be taken by a different session. So a rename mid-task strands nothing, and a genuinely dead handle fails loudly rather than delivering to the wrong agent.

For a long-lived coordinator session, set the handle explicitly. A pinned handle never moves again whatever the title does, which is what you want for something referenced in standing instructions.

Nothing is happening

The most common confusing state, and almost always one of these. In rough order of likelihood:

CheckWhat you would see
Is autonomy paused? The strip under the header is visible. The shared budget is spent — or an unattended window lapsed, which parks everything at once. Allow more, or lift it.
Is mail waiting on you? A count and a Deliver button in the strip. An agent reporting its message was "queued because the recipient is busy" may actually be waiting on your approval — the receipt cannot tell the two apart.
Is something blocked in another session? The N waiting counter in the header covers all sessions. Click it to jump to the oldest one. A whole family can be stalled behind one unanswered question.
Is the child actually there? Families are collapsed by default. A parent that delegated work looks childless until you open the twisty.
Is a session flapping? Automatic retries spend the same shared budget as real work. One session failing in a loop can quietly consume the allowance for everything else. Look for a session on attempt 2 or 3.
Is it waiting out a limit? A parent's delegation bubble says so, with an estimate. This resolves itself — except for a billing block, which never retries and needs you.
Did it give up? Failed — retries exhausted after three attempts. Continue it yourself, or message it asking it to resume.
Two things that are never the cause

Watching a session does not refill the budget — spectating is not directing, and no amount of looking at it will start work. And Stop does not release held mail, so stopping something to "clear" a jam will not unblock the queue; approving or continuing will.
