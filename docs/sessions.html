Using it

Many sessions

Sessions run side by side, in different projects, on either backend. Some of them have children. This page covers the list, the two different kinds of child, and what each Stop button actually stops.

The session list

The ☰ panel lists every session across both backends in one place, split into Active and Archived tabs. You can show them flat or grouped by project. The session you are in has an accent left border.

A session's title is whatever you renamed it to; failing that, the backend's own summary of it; failing that, your first prompt. Both backends title their own sessions, so a title you did not write is normal. The meta line under it shows the project path, the time, the backend, and whether it is archived.

What the dots mean

DotState
solid greenA turn is running.
pulsing accentWaiting for you to approve a tool call.
pulsing purpleWaiting for you to answer a question.
noneIdle.

If a session is waiting on both, the question wins the dot. You can move the badge to the other side of the title in settings.

Row actions

Hover a row and its actions appear — they are invisible otherwise, which is the single most common thing people miss here.

ActionWhat it does
Opens that session in a new browser tab. A real link, so middle-click and copy-link work.
double-click titleRenames it inline. Enter saves, Escape cancels, clicking away saves.
ArchiveMoves it to the Archived tab.
DetachNested rows only. Promotes the session to a root. Below.
UnarchiveArchived rows only. Returns it to Active.
DeleteArchived rows only. Below.

Sessions you cannot reach

A session lives in a directory. If that directory is not reachable from the current container, the session cannot be driven — it still exists, but it has no actions. By default these are summarised as a count; you can hide them, or show them greyed out with a tooltip saying where they were last used.

Starting one

+ New chat opens a picker rather than immediately creating anything. You choose a backend — Claude Code or OpenCode — and a project, with the current one listed first. You can type a custom subdirectory path instead and confirm it with Enter.

Nothing exists on the backend until you send the first prompt; the browser holds your choices until then. Closing the picker without choosing simply abandons the idea.

Gotcha · The backend choice is permanent

A session is bound to its backend when it is created, and there is no way to move it afterwards. If you want the same task on the other backend, start a new session — or have an agent delegate it, which is exactly the case delegation handles well.

Families

When a session spawns another, the child is nested under it in the list, indented, behind a twisty. The subtree is shown depth-first, and the family sorts by its most recently active member rather than by the parent alone — so a family stays near the top while any of its members is working.

A collapsed parent shows an aggregate badge counting everything in its subtree that wants your attention, so a child blocked on a permission cannot hide inside a folded family.

Gotcha · Families start collapsed

A session that has spawned children looks childless until you open the twisty. If you delegated work and cannot find the child, this is almost always why.

Sub-agents & the roster

There are two different things that an agent can create, and telling them apart saves a lot of confusion:

Sub-agentDelegated session
Where you find it The roster (↳ N in the header) A nested row in the session list
Is it a session? No — a task running inside its parent's turn Yes — real, with its own handle and transcript
Can you talk to it? No. Read-only transcript, no composer Yes, like any session
Outlives its parent? No Yes
Make it independent Keep Detach

The roster button reads ↳ followed by how many are running, or the total. Each row gives you the sub-agent's type and description, plus a meta line with its status, a short written summary of what it is doing, its last tool, tokens used, how long it has been going, and its backend. A row's dot shows waiting ahead of running, because waiting is the state that needs you.

Running rows offer Stop. Stopped rows offer Forget, which removes the row but keeps the transcript.

Worth knowing · Opening a blocked sub-agent lands on the blocker

Clicking a row that is waiting takes you into that sub-agent's transcript and scrolls straight to the permission or question card it is stuck on, rather than dropping you at the end and making you hunt.

Keep and Detach

Both cut a child loose from its parent. Which one you get depends on which kind of child it is.

Keep — promoting a sub-agent

A sub-agent's own transcript carries a banner instead of a composer, with a link up to the parent and a Keep button. Keeping it severs the parent link and turns it into an ordinary session: the composer, model picker, mode picker and auto-approve all come back, it is listed on its own, and archiving or deleting its former parent no longer sweeps it away.

Keep is unavailable while the sub-agent is still running — including while it sits parked on a permission request, which looks idle but is not.

Gotcha · A kept sub-agent starts with an empty context

The transcript is preserved and you can read all of it, but the model has not. A sub-agent ran inside its parent's process, so promoting it gives you a fresh session that happens to have a transcript attached — the new session knows nothing of what is written there. Treat the transcript as reference material, and re-state anything the agent needs to act on.

Detach — un-nesting a delegated session

Offered on nested rows, beside Archive and Delete. The row visibly un-indents and becomes a root session, no longer swept up by its former parent's lifecycle. The session itself is unaffected — it was always real; only its place in the tree changes.

Detach does not reset how deep it is

Sessions can only be spawned six levels deep along the chain that actually created them. Detaching changes the display and the lifecycle, not that lineage — a detached session still counts as however deep it was born. See Running unattended.

Stopping things

Three different stops with three different blast radii. The distinction is worth learning, because the obvious guess — that Stop halts everything beneath the session — is not what happens.

ControlStops
Stop
(the red button)		 This turn. It cascades along what the turn is waiting on: its own running sub-agents, and any delegated child it is blocked waiting for. It does not touch delegated children from earlier turns that are off running on their own.
Stop subtree This session and every descendant under it in the tree. Also discards mail addressed into that subtree, so it cannot immediately wake itself back up.
Stop everything Every session with a turn in flight. Asks for confirmation.
Why Stop spares older delegated children

A delegated session you started yesterday is doing its own work, not this turn's. Stopping an unrelated turn today should not kill it. If you do want it stopped, stop it from its own session, or use Stop subtree.

Only sub-agents that are genuinely running get stopped, so finishing work is never retroactively relabelled as killed. If a backend cannot stop a particular sub-agent the row says can't stop rather than pretending. Claude Code only — stopping an individual sub-agent is a Claude Code capability.

Gotcha · Stop does not release held mail

Stop means "do less", so it deliberately leaves parked mail parked. Continue, approving a message, and lifting the autonomy cap all mean "do more" and release it. See Sessions talking.

Archive & delete

Archive is one click with no confirmation. If you archive the session you are looking at, the viewer moves you to the most recent other active session, or to a fresh one if there isn't another.

Delete is only offered on archived rows, and is disabled for the session you are currently viewing — it says switch away first. The normal path is therefore archive, then delete.

Gotcha · Looking for Delete on an active session

It isn't there and it isn't broken. Archive it first; Delete appears on the Archived tab.

Deleting a session with a family

A childless session gets a plain confirmation. One with children gets a dialog that spells out the consequences:

  • Delegated children are listed individually, each with an also delete? checkbox. They are pre-ticked only for children you never messaged — on the assumption that a child you have talked to is one you may still want. Unticking keeps that child; it becomes a root session.
  • Sub-agent transcripts go with the parent, and there is no option to keep them. If you want one, use Keep before deleting the parent.

Escape or clicking the backdrop cancels.
