Using it

Running unattended

How much work agents may do without you, what happens when that runs out, and what the system does on its own when a provider limit or a stall interrupts things.

The autonomy control

One button, in the third column of settings. Its label is a sentence describing what the system is currently doing — Pause after 20 automatic turns, or Run unattended until 08:00. Clicking it opens a menu of choices; nothing commits until you pick one.

ModeOptions
Supervised Pause after 5 / 10 / 20 / 50 / 100 automatic turns, or a number you type. 20 is the default.
Unattended Run for 1 hour, for 4 hours, until 8:00 AM, until a time you pick, or indefinitely.

These are two modes of one choice, not two settings that could contradict each other. Picking a supervised option while a window is running also ends that window — which is the obvious thing to reach for when you want supervision back.

Times are worked out by your browser and sent as an absolute moment, so "until 8:00 AM" means 8am where you are, regardless of what the container thinks the time is.

Spending and refilling

There is one counter for the whole system. Not one per session, not one per delegation chain. Every automatic turn anywhere — mail being delivered, a delegated session starting, a parked message being released — spends from the same budget.

Refills the budgetDoes not
  • Sending a prompt
  • Clicking Continue
  • Answering an approval or question
  • Any autonomy menu action
  • Pressing Stop
  • Scrolling or expanding a bubble
  • Switching session
  • Returning to the tab
  • Watching a session work

The distinction is deliberate: only acts that mean you are directing this count. Merely being present does not, because a stray trackpad brush should not silently hand out another twenty turns.

Gotcha · Budgets do not compose down a tree

A delegated session does not get its own allowance. Because the counter is shared, one session failing in a loop can consume the budget for everything else. If work stops unexpectedly across several unrelated sessions, look for the one that is churning.

Gotcha · The counter keeps climbing while unattended

An unattended window does not pause the counter, it ignores it. So when the window lapses the counter is already far past its limit and everything parks at once. This is why you can come back to a morning where nothing is running and nothing looks broken.

Choosing Cap it now ends a window and resets the counter, so asking for supervision back does not immediately park everything.

The three limits

Autonomy is bounded in three independent ways. They answer different questions, and hitting one tells you nothing about the others.

LimitDefaultBounds
Automatic turns 20 How long a cascade can run before you are consulted. Global.
Fan-out per turn 8 How wide one turn can go — messages and delegations combined.
Creation depth 6 How deep sessions may spawn sessions.

Depth is counted along the chain of who originally created whom, so detaching a session does not reset it. A model that guesses a bad model id is refused before any of this is charged, so guessing costs nothing.

When it pauses

Reaching the limit does not stop you. Human work always runs — you can type, Continue, or answer a card at any time. What stops is automatic work:

  • New automatic turns are refused.
  • Incoming mail is parked, not dropped, and flows when you resume.
  • Delegation is refused up front, so no child is created that cannot start.

A strip appears under the header — outside the scrolling conversation, because the condition is global — offering Allow 20 more, Don't pause, Cap it now, and Stop everything, plus the list of held mail.

The strip is reactive; settings is where you arrange things

The strip only exists when there is something to act on, so it cannot tell you the policy during normal operation. To set up a run before walking away, use the autonomy control in settings.

Gotcha · Stop does not release parked mail

Stop means "do less". It resets the counter, but deliberately leaves held mail held — otherwise stopping something would immediately start everything else. Continue, approving, and the autonomy actions all release it.

When something breaks

Failures are sorted into four kinds, because they need different responses:

KindMeaningRetried?
transientA connection or process died.Yes — after 1, 5, then 15 minutes.
overloadedThe provider is busy.Yes — after 5, 15, then 60 minutes.
rate limitedAn allowance is temporarily spent. Clears on its own.Yes — same slower ladder.
out of creditA hard billing block.Never. Only you can fix it.

When a provider states when an allowance resets, that time is used instead of the ladder, plus a 45-second margin — being a second early costs a whole extra wait. Each session also gets up to 20 seconds of its own spread, because a usage limit belongs to your account rather than to one session; without it, every waiting session would wake at the same instant and trigger the limit again.

A dead turn never looks finished

A turn that was killed, stalled or errored is recorded as such, and is never displayed as merely idle. In a parent's delegation bubble that is the difference between waiting out a usage limit — resuming in ~41m and failed — retries exhausted, needs you. A stop you performed yourself reads as stopped by you and is not coloured as a fault.

Automatic recovery

A supervisor checks every 60 seconds for turns that died and should not have. It restarts turns that crashed, stalled, or errored — up to three attempts, after which it stops and waits for you.

Two things it deliberately will not do:

  • It never resumes something you stopped. Resuming work a human halted on purpose would be the worst thing it could do.
  • It never retries a billing block, because no amount of waiting will clear one.

Every resume prompt tells the agent not to start over — restarting from scratch is the expensive failure — and warns that the result of whatever tool was in flight is unknown, so it should check the state of things before assuming anything succeeded. An automatic resume also tells the agent plainly that no human has reviewed what happened, so it does not assume its work was approved.

Turns that go silent are noticed too. OpenCode turns are probed after 5 minutes of silence; a session that is waiting on you is exempt, since that is not a stall.

Gotcha · Automatic retries spend the shared budget

Each one counts as an automatic turn, exactly as a delivered message would. This is intentional — if retries refilled the budget instead, one crash-looping session would hand every other session a fresh twenty turns, forever. The practical consequence is that a flapping session quietly eats the allowance you were saving for real work.

While a session is waiting to be retried, the Continue strip says so — including which attempt it is on and roughly when the next one is due — rather than offering you a Continue that would fail the same way.

Arranging a run

Before you walk away, in this order:

  1. Set the window first. Pick an unattended duration that covers the work, from the autonomy control. Doing this afterwards means hitting the wall, then lifting the cap, then waiting again.
  2. Deal with permissions. Use Always allow on the cards for things the work needs — it persists. Auto-approve does not survive a driver restart, so it is the weaker choice here.
  3. Turn on auto-delivery for any session that should receive mail while you are not watching. Delegated sessions already have it.
  4. Enable notifications if you want to be told about a question that blocks everything.
  5. Check nothing is already flapping, since retries share the budget with the work you are setting up.
Size the window to the work, not the night

The window does not extend itself, and when it lapses everything parks immediately. A window that is comfortably longer than the job is cheaper than discovering at 7am that it ended at 2am.
